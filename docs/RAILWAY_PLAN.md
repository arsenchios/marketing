# Новая установка ArsLive

Все ресурсы создаются отдельно. Исходную платформу, её базы, OAuth, ключи и записи не подключать и не переносить. Этот файл — инструкция, а не подтверждение deployment.

## 1. Railway

Создать новый проект и сервис из `arsenchios/marketing`, ветка `main`. Dockerfile содержит Node, FFmpeg, Poppler, LibreOffice и проверку изолированного конвертера презентаций. Добавить PostgreSQL и постоянный volume в `/data`. Оставить одну реплику. Подключить свой домен и HTTPS.

Установить переменные в интерфейсе Railway, не в репозитории:

| Переменная | Что указать |
| --- | --- |
| APP_MODE | `public` |
| APP_ORIGIN | Канонический адрес, например `https://live.example.com`, без завершающего слеша |
| DATA_DIR | `/data` — путь volume |
| DATABASE_URL | URL новой PostgreSQL |
| GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET | Новое OAuth-приложение Google |
| OWNER_EMAIL | Почта администратора новой платформы |
| TOKEN_ENCRYPTION_KEY | Новый случайный ключ: 32 байта в base64; хранить резервную копию отдельно |

`PORT` задаёт Railway. Схема PostgreSQL — `arslive`; даже при этом рекомендуется отдельная база. Без обязательных настроек публичный сервер показывает режим настройки и блокирует вход. `/api/health` в этом режиме доступен, поэтому один успешный healthcheck ещё не означает готовую платформу.

## 2. Вход Google и YouTube

В новом Google Cloud project включить YouTube Data API v3. Создать OAuth client типа Web application, настроить consent screen и необходимые проверку приложения / test users. Разрешить HTTPS origin из APP_ORIGIN и redirect URI:

- `https://live.example.com/api/auth/google/callback`
- `https://live.example.com/api/integrations/youtube/callback`

Войти с OWNER_EMAIL, открыть кабинет и подключить свой YouTube-канал. Для доставки через YouTube включить `YOUTUBE_LIVE_ENABLED=true`. Канал должен поддерживать прямые эфиры и их встраивание. Приложение создаёт видео «по ссылке» (unlisted), а не публичное в ленте канала; это не YouTube private: знающий ссылку может открыть видео. Режим private мешает обычному встроенному просмотру зрителей.

Новый канал не наследует разрешения, токены или проверки старого. Проверить реальный короткий эфир с телефона и другого подключения, а затем завершение и появление записи. Проверки локальными заглушками не заменяют эту проверку.

## 3. Приватные записи Cloudflare R2

Создать отдельный приватный bucket и ограниченный токен только на него. Указать `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`. Не включать публичный доступ. Сохраняется локальная копия на volume, а очередь переносит запись в R2 и проверяет объект. Срок хранения в приложении — 7 дней; скачать нужные записи заранее. Добавить отдельную резервную копию PostgreSQL. Не использовать общий bucket с исходной платформой.

## 4. Второй спикер в разных сетях

STUN уже используется. Для сетей, где прямое соединение невозможно, подключить TURN: `CLOUDFLARE_TURN_KEY_ID` и `CLOUDFLARE_TURN_API_TOKEN` либо `SPEAKER_ICE_SERVERS` с собственной конфигурацией. TURN — отдельный инфраструктурный ресурс с собственными условиями оплаты; репозиторий его не создаёт. Постоянный мастер-ключ остаётся только на сервере.

## 5. Приёмка перед клиентским эфиром

Проверить Google-вход администратора и клиента, доступ к чужим вебинарам, загрузку PDF/PPTX/изображений, ведущего и спикера в разных сетях, зрителя на iPhone и компьютере, переподключение, звук, завершение, локальную/R2/YouTube записи. Проверить восстановление из резервной копии. Не запускать публикацию с перезапуском сервиса во время эфира.

Не увеличивать `numReplicas` и не запускать два процесса на одной базе: медиасостояние привязано к одному процессу. Несколько одновременных эфиров — отдельный этап архитектуры.
